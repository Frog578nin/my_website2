До университета моей системой контроля версий были папки: `проект`, `проект_финал`, `проект_финал2`, `проект_финал2_ИСПРАВЛЕНО`. Так делали все, кого я знаю. Это работает ровно до того дня, когда нужно вспомнить, что именно поменялось между «финалом» и «финалом2». Дальше не работает.

Git решает задачу по-настоящему. Он хранит полную историю проекта: каждое сохранённое состояние, кто его сделал, когда и с каким комментарием. Сохранённое состояние называется коммитом. Можно открыть любой старый коммит, сравнить два коммита построчно или откатить весь проект к прошлому вторнику.

На практике я обхожусь небольшим набором команд:

```bash
git status          # что изменилось
git add file.md     # подготовить изменение
git commit -m "Добавил раздел об образовании"
git push            # отправить коммиты на GitHub
git log --oneline   # история
```

Это закрывает процентов девяносто моей работы. Под капотом есть ветки, слияния и rebase, и понимаю я их примерно на уровне «однажды читал туториал». Для персонального сайта простой линейной истории хватает.

Вторая половина истории — GitHub. Сам Git локален, GitHub же хранит репозиторий в сети. Мой репозиторий открытый, и поначалу это было неуютно, как оставить тетрадь раскрытой на парте. Потом я понял, что её всё равно никто не читает, а если и прочитает — ладно, сообщения коммитов у меня приличные.

Самое приятное происходит после `git push`. У сайта настроен GitHub Actions: каждый пуш в главную ветку запускает сборку, и через пару минут новая версия уже в сети. Руками я не загружаю ничего. Когда это сработало впервые, я запушил исправление опечатки просто чтобы посмотреть, как робот делает свою работу.

Одна привычка, которую я стараюсь выработать: писать в коммитах «зачем», а не «что». «Поправил конфиг» будущему мне не говорит ничего. «Прописал baseURL, чтобы на GitHub Pages грузился CSS» — это записка от прошлого меня будущему. А прошлый я — обычно единственная документация, которая у меня есть.
